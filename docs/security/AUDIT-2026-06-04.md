## 1. Résumé exécutif

**Posture globale : correcte sur l'isolation, perfectible sur l'authentification fine, l'anti-fraude et l'hygiène d'abus.**

La propriété de sécurité n°1 — **l'isolation entre commerçants** — **tient** : aucun IDOR cross-tenant confirmé. Toutes les routes dérivent le marchand de la session (jamais d'un id client), l'ownership `merchant_id` est vérifié partout où un id transite, l'autorisation admin et l'anti-escalade de rôle sont robustes (trigger DB + contrôle applicatif via `getUser()`), la RLS est activée sur 100 % des tables tenant, et aucun secret n'a jamais été committé. Pas de XSS (`dangerouslySetInnerHTML` absent), pas de SSRF, pas d'open redirect, comparaison des tokens Wallet en temps constant, CVE Next.js middleware non exploitable.

Les faiblesses réelles se concentrent sur : (1) l'**anti-fraude fidélité** (scan/redeem non atomiques, anti-rejeu absent), (2) l'usage de **`getSession()` au lieu de `getUser()`** pour autoriser 6 routes mutantes, (3) le **contournement des rate-limits par IP** (spoof `X-Forwarded-For`), (4) la **conformité RGPD** (effacement incomplet), et (5) une **surface d'abus/DoS** (endpoints coûteux ou publics sans rate-limit).

### Top 5 des risques
1. **SEC-01 — Fraude fidélité** : QR statique sans anti-rejeu + idempotence contrôlée par le client + scan/redeem en *read-then-write* non atomique → multi-tampons et double-encaissement fiables. (Élevé→Critique selon modèle commission/cashback.)
2. **SEC-02 — Autorisation sur `getSession()`** (cookie non revalidé) dans 6 routes qui écrivent via service-role (scan, redeem, customers PATCH/DELETE, generate-apple/google-pass). (Élevé.)
3. **SEC-03 — Rate-limits par IP contournables** via spoof `X-Forwarded-For` → brute-force login horizontal + enrôlement de masse. (Élevé.)
4. **SEC-04 — RGPD** : `DELETE /customers/[id]` laisse des données résiduelles (`wallet_device_registrations`, `campaign_sends`). (Moyen.)
5. **SEC-06/07 — Abus/DoS** : `/wallet/apple/v1/log` public non limité + analytics/exports/géocodage sans rate-limit. (Moyen.)

## 3. Détail des findings

### SEC-01 · Fraude fidélité : scan/redeem non atomiques + anti-rejeu absent — **Élevé**
**Acteur & scénario.** Un commerçant/insider (authentifié, possède le QR statique de ses clients), ou un client porteur du QR : le QR Wallet est `cardId:HMAC(cardId)`, **constant dans le temps** (aucun nonce/horodatage/expiration). La protection d'idempotence du scan dérive d'un header `idempotency-key` **fourni par le client**, et le front en génère un **frais à chaque scan** → collision impossible, donc protection nulle. Enfin scan et redeem font *lire → calculer en mémoire → écrire* sans verrou ni update conditionnel atomique : deux requêtes concurrentes contournent le cooldown et double-comptent / double-encaissent.
**Preuve.**
- `src/lib/qrSignature.ts:8-12` — signature ne dépend que de `cardId`, pas de nonce/exp.
- `src/app/api/scan/route.ts:40` (clé d'idempotence depuis header client) + `src/app/scan/page.tsx:35` (`idempotency-key: crypto.randomUUID()` à chaque appel).
- `src/app/api/scan/route.ts:50` (read) → `:69` (calcul) → `:81-84` (write) — non atomique ; cooldown `:62` lit `last_scan` non verrouillé.
- `src/app/api/redeem/route.ts:43` (check mémoire) → `:50-51` `.update({ stamps_count: 0 }).eq("id", …)` **sans** `WHERE stamps_count >= goal` ; aucune idempotence sur redeem → double-reset = double récompense.
**Impact.** Multi-tampons et double-encaissement de récompenses exploitables de façon fiable ; cooldown anti-spam contournable en rafale concurrente. Pas de solde négatif (reset fixe). Sévérité **Critique** si un modèle de commission/cashback est adossé au volume de scans.
**Remédiation.** Rendre scan et redeem **atomiques et conditionnels** côté DB (RPC/`UPDATE … SET stamps_count = stamps_count + 1, last_scan = now() WHERE id = $1 AND (last_scan IS NULL OR last_scan < now() - interval) RETURNING …` ; redeem `… SET stamps_count = 0 WHERE id = $1 AND stamps_count >= goal RETURNING …`) ; n'écrire l'audit/notif que si une ligne a été modifiée. Ancrer l'anti-rejeu dans l'état serveur (nonce consommé, ou clé d'idempotence stable non choisie par le client).

### SEC-02 · Autorisation via `getSession()` (non revalidé) — **Élevé**
**Acteur & scénario.** `getSession()` (côté serveur, `@supabase/ssr`) reconstruit `session.user` **depuis le cookie sans revalider le JWT auprès du serveur Auth** ; `getUser()` revalide. Un cookie périmé/révoqué non rejeté autorise alors une action. Ces routes écrivent ensuite via **service-role** (RLS contournée).
**Preuve (toutes en autorisation, pas affichage) :** `src/app/api/scan/route.ts:17`, `src/app/api/redeem/route.ts:16`, `src/app/api/customers/[id]/route.ts:25` (DELETE RGPD) et `:114` (PATCH), `src/app/api/generate-apple-pass/route.ts:15`, `src/app/api/generate-google-pass/route.ts:13`. (Le reste du code utilise correctement `getUser()` : `adminAuth.ts:13`, `analytics/merchant.ts:5`, `proxy.ts:29`, `mfa-event:10`.)
**Impact.** Décision d'autorisation sur un jeton non revalidé, sur des routes mutantes service-role. Exploitabilité réelle limitée (le JWT est signé ; le risque concret = jeton expiré/révoqué non rejeté) → `[À VÉRIFIER]`, mais c'est un écart net avec la recommandation officielle Supabase.
**Remédiation (quick win).** Remplacer `getSession()` par `getUser()` dans ces 6 routes (le code utilise déjà `user.id` ; correctif trivial, déjà le pattern ailleurs).

### SEC-03 · Rate-limit par IP contournable (spoof `X-Forwarded-For`) — **Élevé**
**Acteur & scénario.** La clé IP est dérivée du **premier** segment de `X-Forwarded-For` (valeur fournie par le client). En variant cet en-tête, l'attaquant obtient une clé différente à chaque requête → les limiteurs par IP (`login-ip` 20/15min, `enroll-ip` 15/h, `enroll-artifact` 60/h) sont contournés.
**Preuve.** `src/lib/auditLog.ts:46-48` — `xff?.split(',')[0]?.trim()`.
**Impact.** Brute-force login horizontal (atténué par le limiteur **par email** 5/15min, lui non contournable), enrôlement/spam de masse, pollution `audit_logs.ip_address` avec des IP forgées.
**Remédiation (quick win).** Utiliser l'IP de confiance de la plateforme (`x-real-ip` injecté par Vercel, ou `ipAddress(req)` de `@vercel/functions`), ou le dernier hop de confiance de XFF. Ne jamais faire confiance au premier segment.

### SEC-04 · Effacement RGPD incomplet — **Moyen**
**Acteur & scénario.** `DELETE /api/customers/[id]` s'appuie sur les CASCADE DB (`customers → loyalty_cards → scan_history`), mais **deux tables sans FK/cascade conservent des données** : `wallet_device_registrations` (push token + `serial_number` = id de carte) et `campaign_sends` (`card_id`).
**Preuve.** `src/app/api/customers/[id]/route.ts:87-91` (seul `customers.delete()`) ; `supabase/migrations/20260531_push_wallet.sql:5-13` (registrations sans FK) ; `supabase/migrations/20260603_campaigns.sql:17-22` (`campaign_sends.card_id` sans FK).
**Impact.** Conformité RGPD art. 17 partielle ; identifiants techniques rattachables persistants.
**Remédiation.** Dans la route DELETE, purger explicitement `wallet_device_registrations WHERE serial_number IN (card_ids)` et `campaign_sends WHERE card_id IN (card_ids)` (les `card_ids` sont déjà collectés `route.ts:69-72`), ou ajouter des FK `ON DELETE CASCADE`.

### SEC-05 · PII email en clair dans `audit_logs` immuable — **Moyen**
**Preuve.** `src/app/api/auth/login/route.ts:40,58,78` (email brut dans `details` à chaque login, y compris échecs/non-inscrits) ; `src/app/api/admin/merchants/route.ts:77`. Journal append-only (triggers `no_update`/`no_delete`) → non purgeable.
**Remédiation.** Masquer via `maskEmail()` (`src/lib/log/mask.ts:7`) avant écriture, ou stocker un hash.

### SEC-06 · `/wallet/apple/v1/log` non authentifié, non limité, log brut — **Moyen**
**Preuve.** `src/app/api/wallet/apple/v1/log/route.ts:3-10` (`console.log(JSON.stringify(body).slice(0,500))`, aucune auth ni rate-limit).
**Impact.** Injection/empoisonnement de logs, spam/coût d'ingestion, PII potentielle.
**Remédiation.** Rate-limit par IP, ne pas logger le body brut (échapper les `\n` / whitelister), ou log-sampling. Garder le 200 (requis PassKit).

### SEC-07 · Routes coûteuses sans rate-limit — **Moyen**
**Preuve.** Aucun `rateLimit()` sur : `analytics/route.ts:8`, `analytics/export/pdf/route.ts` (renderToBuffer @react-pdf, CPU), `analytics/export/csv`, `segments/*`, `campaigns/*`, `dashboard-config`, `merchant/location` (géocodage facturé), `auth/mfa-event`.
**Impact.** DoS/épuisement CPU et coûts par un commerçant authentifié (ou compte compromis). Création illimitée de campagnes → amplification au cron.
**Remédiation.** `rateLimit('<prefix>:${merchantId}', …)` sur ces routes (motif déjà utilisé `notifications/send:14`) ; quota strict sur l'export PDF et le géocodage ; plafonner le nb de campagnes/marchand.

### SEC-08 · CSP absente (+ Permissions-Policy) — **Moyen**
**Preuve.** `next.config.ts:11-29` ne pose que HSTS, X-Content-Type-Options, X-Frame-Options, X-XSS-Protection, Referrer-Policy. Aucune `Content-Security-Policy` ni `Permissions-Policy` (recherche globale vide).
**Remédiation.** CSP stricte (idéalement nonce-based Next 16) : `default-src 'self'; script-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'`. Ajouter `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`.

### SEC-09 · `auth_token` Wallet en clair, sans rotation/expiration — **Moyen**
**Preuve.** `supabase/migrations/20260531_push_wallet.sql:1` (`auth_token TEXT`, pas de hash) ; `src/lib/wallet/authToken.ts:24-31` (génération 128 bits + comparaison du token clair). Aucune colonne d'expiration ni logique de rotation.
**Impact.** Bearer en clair pour toute la vie de la carte ; compromission DB = compromission de tous les pass. Atténué : entropie 128 bits, comparaison temps constant, RLS deny-all (lecture service-role seule).
**Remédiation.** Stocker un **hash** (SHA-256) et comparer le hash ; colonne d'expiration/rotation ; révocation = régénérer le pass.

### SEC-10 · Identifiants admin démo réels committés — **Moyen**
**Preuve.** `docs/COMPTES-DEMO.md` (tracké) : mot de passe `‹DEMO_ADMIN_PASSWORD›` + UUID Auth admin ; fallback identique `scripts/reset-demo-admin-password.mjs:16`. (Le compte perso `thealphawa@gmail.com` n'a pas de mot de passe stocké — OK.) Repo privé (atténuant) mais le mot de passe vit dans l'historique git.
**Remédiation.** Retirer le mot de passe du doc + du fallback (exiger `DEMO_ADMIN_PASSWORD` sans défaut) ; faire tourner le mot de passe admin-démo en prod ; supprimer ce compte une fois les tests finis.

### SEC-11 · Anti-fraude jamais appliqué en temps réel — **Moyen**
**Preuve.** `evaluateSignals`/`fetchMerchantFlags` ne sont appelés que dans des pages d'affichage (`src/app/admin/page.tsx:26`, `src/app/dashboard/security/page.tsx:13`) ; aucun import `antifraud` dans `scan/route.ts` ni `redeem/route.ts`.
**Impact.** Détection rétrospective et purement informative ; rien n'est bloqué/throttlé en temps réel.
**Remédiation.** Brancher une vérification temps réel (compteur Redis ou `evaluateSignals`) dans scan/redeem qui bloque/met en quarantaine au-delà des seuils + alerte admin.

### SEC-12 → SEC-23 (Faible / Info) — détail synthétique
- **SEC-12** `CRON_SECRET` : `src/app/api/cron/campaigns/route.ts:16-18` compare via `!==` (non constant-time). Utiliser `safeCompare` (`authToken.ts:11`). (Cron par ailleurs fail-closed si secret absent — bon.)
- **SEC-13** QR HMAC : `src/lib/qrSignature.ts:10` tronqué 16 hex (64 bits) ; `:23` comparaison `!==`. Garder le HMAC complet + `timingSafeEqual`.
- **SEC-14** Sentry : `src/lib/monitoring/scrub.ts:24-41` ne scrub que request/user/extra/contexts — pas `event.message`/`exception`/`breadcrumbs` ; et `src/app/api/generate-google-pass/route.ts:119` logue l'objet erreur entier (fragment de `private_key` possible). Étendre le scrub + logger `error.message`.
- **SEC-15** CSV injection : `src/lib/analytics/csv.ts:1-4` `cell()` n'échappe que `" , \n`, pas `= + - @`. Champs client (`full_name/email/phone`, segments `name`). Préfixer `'` les valeurs débutant par `= + - @ \t \r`.
- **SEC-16** redeem accepte UUID brut : `src/app/api/redeem/route.ts:28-30` — bypass de la présentation du QR client (borné au tenant). Décider si volontaire ; sinon n'accepter que le QR signé.
- **SEC-17** registration : `passTypeId` non validé sur POST/DELETE (`devices/.../registrations/[passTypeId]/[serial]/route.ts`), contrairement au GET pass. Valider `passTypeId === APPLE_PASS_TYPE_ID`.
- **SEC-18** MFA step-up fail-open : `src/proxy.ts:40-47` — si l'appel AAL échoue, `needsStepUp=false` (l'utilisateur passe). Décider fail-closed sur surfaces sensibles.
- **SEC-19** rate-limit sans try/catch (`src/lib/rateLimit.ts:22-31`) : panne Upstash → 500 (fail-closed de fait, mais comportement non explicite ; login sans try/catch). Expliciter la politique.
- **SEC-20** masquage PII non branché : `redactPII/maskEmail/maskName` (`src/lib/log/mask.ts`) utilisés seulement par Sentry. Les brancher avant `logAuditEvent`/`console.*`.
- **SEC-21** `wallet_device_registrations` sans `merchant_id` ni policy (RLS deny-all) → isolation 100 % applicative (`20260531_push_wallet.sql`, `20260602_wallet_tables_rls.sql:9`). Ajouter `merchant_id` + policy (défense en profondeur).
- **SEC-22** `last_scan`/`scan_history` non écrits sur carte pleine (`scan/route.ts:73-78`) → sous-estime l'anti-fraude card_farming. Enregistrer aussi ces scans.
- **SEC-23** `is_admin()` : `EXECUTE` non explicitement restreint à `authenticated` (PUBLIC par défaut) — bénin (la fonction teste l'appelant), durcissement optionnel `REVOKE … FROM PUBLIC`.

## 4. Points vérifiés SAINS (défenses confirmées)

- **Isolation multi-tenant** : aucun IDOR cross-tenant confirmé. Ownership `merchant_id` vérifié sur scan (`:56`), redeem (`:39`), customers PATCH/DELETE (`:60`,`:130`), campagnes (`.eq("merchant_id", …)`), segments/analytics (scoping `loadClassified(merchantId)` + RLS), enroll (token + `merchant_id`). Aucune route n'accepte de `merchantId` depuis l'URL/body.
- **Autorisation admin & anti-escalade** : `requireAdminApi()` en tête des 3 routes `/api/admin/**` ; rôle lu via `getUser()` (non falsifiable) ; trigger DB `enforce_merchant_role_guard()` + CHECK `role IN ('admin','merchant')` bloquent l'auto-promotion ; `role` écrit en dur `"merchant"` à la seule création (admin-only).
- **RLS** : activée sur 100 % des tables tenant ; aucune policy permissive (`USING (true)`/`TO public`) ; `audit_logs` append-only (triggers no_update/no_delete) ; unicité email **par marchand** ; `search_path` épinglé sur `is_admin()` et le trigger.
- **Wallet web service** : token lié au `serial`, comparé en **temps constant** (`timingSafeEqual`) ; serials = UUID v4 (122 bits, non énumérables) ; token 128 bits ; parsing d'en-tête strict.
- **Web** : pas de `dangerouslySetInnerHTML` ; e-mails échappés (`escapeHtml`) + anti-CRLF sur le nom expéditeur ; `pass.json` et PDF non injectables ; X-Frame-Options DENY ; pas d'open redirect ; **pas de SSRF** (Nominatim hôte fixe, entrée en `q=` encodée).
- **Secrets** : aucun secret en `NEXT_PUBLIC_*` ; **historique git propre** (aucun `.env`/`.pem`/`certs` committé ; seules des valeurs dummy) ; erreurs client génériques ; `enrollment_token` = UUID v4 et **réellement invalidé** au `rotate-token`.
- **CVE-2025-29927** (bypass middleware) : non exploitable — Next **16.2.4** patché + autorisation refaite par route/layout.
